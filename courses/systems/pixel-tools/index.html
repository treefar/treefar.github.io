02 · POSITIONING

五工具，一句話定位

兩種產物是硬界線：Asset Forge 與 Crocotile 3D 產「幾何」；PixelOver、Pixelate、PixelBake 產「像素圖」。 後三者互為替代品，前兩者不是。

類別工具一句話定位原生產物在本專案的角色
幾何 Asset Forge 用現成低多邊形積木組模型的組裝台，附 Lua 腳本可程序生成 .model（可再編輯）、匯出 OBJ／GLB／sprite 三型機甲的幾何來源
幾何 Crocotile 3D 把 2D tileset 直接畫進 3D 空間的 tile 建模器 .crocotile（純 JSON，貼圖為 base64 內嵌） 整個瀑布世界的地形、房屋、樹與水
像素圖 PixelOver 把圖片、2D 骨架動畫或 3D 動畫轉成受控像素風的獨立製作工具 PNG／GIF／spritesheet＋JSON（需付費版） 顆粒感最重的那一版頭像，只手動匯出
像素圖 Pixelate Unity 內的像素化擷取套件，設定全是公開欄位、可完全程式驅動 spritesheet PNG（本專案輸出 810×810 網格） 乾淨大色塊風格的比對組
像素圖 PixelBake 本專案自寫的 Unity 像素烘焙器：正交逐幀低解析算繪＋色盤量化＋抖動＋描邊 spritesheet PNG＋PixelPortraits.json HUD 機體頭像的正式來源

03 · TOOL DOSSIERS

各工具檔案

每個工具挑最有代表性的強項、弱項、自動化能力與實測數字，不求逐項窮舉。

幾何工具
Asset Forge
v2.5.3

用現成低多邊形積木組模型的組裝台，附 Lua 腳本可程序生成。

強項
  • Lua API 可程序生成：forge.build、forge.materialColor 等已驗證可用
  • .model 可再編輯，本專案已有原生匯入器，每個積木是獨立 GameObject
弱項
  • 不適合自由雕刻、高模角色或寫實 PBR
  • 匯出 OBJ 會把整台合併成一坨，改一顆零件要重匯整台
自動化能力：半自動。Lua 腳本可跑，但第一次要人工前景選檔；.model 進 Unity 這段全自動。
關鍵實測數字
  • 5 個 .model 全部缺件 0，渲染驗證通過
  • 鏡射回歸 8 案例＋4 項疊加全數通過
  • 三型機甲 GLB：57／64／67 meshes
  • 資源包 1,490 個積木，本專案只抽 30 種，共 806 KB
幾何工具
Crocotile 3D
v2.7.2c

把 2D tileset 直接畫進 3D 空間的 tile 建模器。

強項
  • .crocotile 是純 JSON，貼圖 base64 內嵌，轉檔全程不需開本體
  • 原生匯入器一次產出 atlas、靜態 mesh、UV 動畫、prefab 實例與坡度碰撞
弱項
  • 不是程序化 terrain、高模雕刻或寫實 PBR 的主力
  • 背景工作階段呼叫 saveScene(1) 會毀檔，另存只能在 GUI 內手動做
自動化能力：完全自動，連開都不用開——但只限「讀」。
關鍵實測數字
  • v4 流線世界：4,428 tile／1,069 prefab 實例／49 billboard／75 塊碰撞
  • v2 的 659 實例／29 billboard／40 塊碰撞，與獨立 Node 轉檔器完全一致
  • 靜態驗收 108／108 PASS，動態驗收 19／19 PASS
像素圖工具
PixelOver
v0.18.4

把圖片、2D 骨架動畫或 3D 動畫轉成受控像素風的獨立製作工具。

強項
  • 功能面最寬：indexation（把顏色映射到索引色盤的機制）、dithering、2D 骨架與 IK、shader、粒子、多方向匯出
  • 顆粒感最強：9 格抖動比例 0.523～0.652，三工具中最高
弱項
  • Final Size 唯讀，由模型大小決定，成品尺寸小於另兩邊
  • 匯出 PNG／GIF／spritesheet 需要付費版
自動化能力：不能自動化。沒有命令列匯出 API（2026-08-31 --help 實測）。 GUI 可由桌面自動化代駕完成（2026-09-03 實證），但仍不可排進 CI。
關鍵實測數字
  • 樣本甲　15 色／50,513 不透明／0.586／24.8 KB
  • 樣本乙　15 色／55,235 不透明／0.652／25.3 KB
  • 樣本丙　16 色／51,518 不透明／0.523／23.1 KB
像素圖工具
Pixelate
v2.02

Unity 內的像素化擷取套件，設定全是公開欄位，可完全程式驅動。

強項
  • 可完全程式驅動：-executeMethod 一鍵重跑
  • 色塊最乾淨：9 格抖動比例 0.106～0.125，三工具中最低；檔案也最小
弱項
  • 沒有獨立的抖動參數，也沒有公開的抖動樣式選項
  • Stylized Normal Maps for URP 2D Lights 在本專案（Built-in RP）用不到
自動化能力：可完全程式驅動。但有四個前置條件：不可加 -quit／-nographics、須指派 captureCamera、需自算 orthographicSize。
關鍵實測數字
  • 樣本甲　16 色／87,206 不透明／0.118／18.9 KB
  • 樣本乙　16 色／94,116 不透明／0.106／17.8 KB
  • 樣本丙　16 色／70,022 不透明／0.125／17.2 KB
像素圖工具
PixelBake
本專案自寫

Unity 像素烘焙器：正交逐幀低解析算繪＋色盤量化＋抖動＋描邊。

強項
  • 一鍵重建成立，參數進版控，跟場景組裝同一套 -executeMethod 流程
  • 描邊色跟著固有色壓暗吸附，另外兩個工具都沒有這個選項
弱項
  • 色盤命中會多 1 色（描邊吸附不到色盤時的退回色）
  • 8 方向配 16 色時每方向只剩 2 色階，畫面偏髒
自動化能力：可完全程式驅動。-batchmode -quit -executeMethod PixelBake.PixelBakeMenu.BakeForComparison
關鍵實測數字
  • 樣本甲　17 色／95,694 不透明／0.378／50.8 KB
  • 樣本乙　15 色／102,202 不透明／0.483／56.7 KB
  • 樣本丙　17 色／80,495 不透明／0.438／50.0 KB
  • 抖動生效量測：水平相鄰異色比例 0.353 → 0.551（+56%）

04 · WHEN TO USE WHAT

使用時機：我要做什麼，選哪個

以「我要做什麼」為入口的 12 種情境，對照選哪個工具、為什麼。

#我要做什麼選哪個為什麼
1做一個像素風的 3D 場景、地城、小島或 diorama，素材是 2D tilesetCrocotile 3Dtile 直接畫進 3D，UV 與像素貼圖同步編修
2上面那個場景要進 Unity，而且要能一鍵重建Crocotile → .crocotile 直接拖進 Assets/匯入器同時產 atlas、靜態 mesh、UV 動畫、prefab 實例與坡度碰撞，不需開 Crocotile
3快速組一台低多邊形載具／機甲／建築，之後還要單獨改某一顆零件Asset Forge → .model 原生匯入匯入後每個積木是獨立 GameObject；匯出 OBJ 會合併成一坨
4同一規則下要大量變體Asset Forge Luaforge.build 可程序生成，固定 seed 就能重現
5角色要帶骨架動畫進 UnityAsset Forge → Blender → FBX.model 匯入器產的是逐積木靜態 prefab；骨架與動作要在 Blender 做
6HUD 頭像／小圖示的像素動畫，模型改版後要能一起重烘PixelBake走 -executeMethod，參數進版控
7要乾淨大色塊、輪廓銳利的像素風（UI 圖示、清晰小圖）Pixelate抖動比例 0.118，三者最低，色盤精確 16
8要顆粒重的復古像素質感，做單張美術，可接受手動PixelOver抖動比例 0.586，三者最高
9要八方向像素角色 spritesheetPixelBake 的 Directions，並加大色盤8 方向配 16 色時每方向只剩 2 個色階，畫面會髒
10這一步要放進 CI 或 batchmode 自動跑PixelBake 或 Pixelate；不可排 PixelOverPixelOver 沒有匯出用的命令列 API
11來源是 2D 骨架動畫或單張圖片，不是 3D 模型PixelOver只有它有 2D 骨架與 IK
12Crocotile 場景不進 Unity，要做網頁展示scripts/crocotile-to-unity.jsNode 轉檔器保留給不進 Unity 的用途

決策樹

Q1　產物是 3D 幾何，還是 2D 像素圖？
  • 3D 幾何
    • Q2　素材是 2D tileset、目標是場景／地形／建築群？
      • 是 Crocotile 3D
        • Q3　要進 Unity？
          • 要.crocotile 直接拖進 Assets（原生匯入器）
          • 不要（網頁展示等）scripts/crocotile-to-unity.js
    • Q2′　目標是角色／載具／道具，想用現成積木組？
      • 是 Asset Forge
        • Q3′　要帶骨架動畫嗎？
          • 要Asset Forge → Blender 綁骨與動作 → FBX → Unity
          • 不要，但要能逐零件改.model 直接拖進 Assets
  • 2D 像素圖
    • Q4　來源在不在 Unity 場景裡（有 GameObject 與 AnimationClip）？
      • 在
        • Q5　這一步要能一鍵重跑嗎？
          • 要
            • Q6　要什麼風格？
              • 居中、描邊跟著固有色PixelBake
              • 乾淨大色塊、輪廓銳利Pixelate
          • 不用，只做一次、要顆粒感PixelOver（手動）
      • 不在（外部 GLB、圖片、GIF、2D 骨架）PixelOver
    • Q7　需要 2D 骨架與 IK、shader 預設集、粒子、精細 indexation？
      • 是只有 PixelOver 有，沒有替代品

一句話總結：幾何看素材形態（tileset 走 Crocotile、積木走 Asset Forge）， 像素圖看自動化需求（要一鍵重跑就在 Unity 內解決，不要就用 PixelOver）。

06 · ANTI-PATTERNS

反模式：什麼時候不要用誰

11 條踩過的雷，點開看細節。

01不要把 PixelOver 排進「必須一鍵重跑」的管線
PixelOver 是 Godot release 版打包，命令列只有 Godot 通用參數，沒有匯出 API（2026-08-31 用 --help 實測）， 一律只能操作 GUI 匯出。2026-09-03 已用桌面自動化代駕補齊 樣本乙、樣本丙 兩台的 GUI 匯出，但那是操作介面代打，不是命令列 API； 三個踩坑是路徑欄不可貼上、匯出後會悄悄崩潰重啟、超寬螢幕要先把介面 Scale 調 200%。「排進 CI」仍然不可行——要自動化就換 PixelBake 或 Pixelate。
02不要用背景工作階段對 Crocotile 場景做另存
saveScene(1) 會毀檔：3,381 個 tile 存完只剩 15 個 mesh。另存只能在已啟用的 GUI 裡手動做。 驗收時要把「原生載入成功」與「原生 round-trip 儲存成功」分開標示，不可混為一談。
03不要把視覺 OBJ 直接指派給 MeshCollider
Unity 6000.5.3 的 Editor 與 build 都會過，但 Windows Player 載入 level0 會報 corrupted / Position out of bounds。 一律用預先切好、每塊不超過 128 三角形的分塊碰撞。本專案 v2 切成 40 塊、共 2,956 triangles。
04不要在解析度不同的情況下比抖動密度
第一次比對 PixelBake 是 64px、PixelOver 是 162px，量出 0.581 對 0.586 幾乎一樣——那是假象，低解析度下相鄰像素本來就容易不同色。 統一成 162px 後才變成 0.378 對 0.586。
05不要只看匯入統計數字就宣稱資產正確
detail_antenna.obj 有 3 個 group（對應三個材質槽），Unity 的 OBJ 匯入器把每個 group 拆成子 GameObject， 而匯入器只抓到第一個。統計全部正常——放置 7、缺件 0、烘鏡射 2、零警告——只有渲染出來才看得到 y 範圍從 [0, 1.0] 只剩 [0, 0]。 資產類驗收一定要加一張真的渲染圖。
06不要把 Crocotile 匯入器的座標處理抄到 Asset Forge 匯入器
Asset Forge 本身是 Unity 應用，.model 的座標已經是 Unity 左手座標，不換手性； Crocotile 是 Three.js 右手系，必須翻。兩個匯入器這一段不可互抄。 另外處理負縮放時，關鍵是行列式的正負而不是「任一軸為負」——(-1,-1,1) 兩個負號相乘為正，不可翻繞序。
07不要在 -nographics 下做截圖或取色
沒有 GPU，Graphics.Blit 不會畫，讀回來全是空白。Asset Forge 的預覽截圖與 Pixelate 的擷取都不能加這個參數。 同理 Pixelate 也不能加 -quit，擷取是協程，Unity 會在跑完前關掉。
08不要用 Asset Forge 匯出的 OBJ 當「還可以再改」的資產
匯出會把整台合併成一坨，改一顆零件要重匯整台；要逐零件可編輯就走 .model 原生匯入。
09不要一次給 Unity 多個 -importPackage
只會生效一個，而且 exit 0、錯誤 0，套件根本沒進來。要分開跑。
10不要把會隨世界大小變的數字寫死進驗收
碰撞塊數從 v2 的 40 變成 v4 的 75，驗收改成驗性質：至少 20 塊、每塊 mesh 非空、單塊不超過 400 三角形。
11不要把 8 方向配 16 色當預設
色盤要涵蓋所有角度，每個方向只分到 2 個色階，畫面偏髒；程式雖然會發警告，但預設值不改就是髒的。

對齊了什麼 — 動畫 Patrol、每格 162×162、16 色、8 幀、正交四分之三視角 (12, 150, 0)、Padding 1.08、抗鋸齒全關。 Pixelate 與 PixelBake 用同一條取景公式（orthographicSize = max(高,寬)/2 × 1.08），兩邊模型一樣大； PixelOver 的 Final Size 唯讀，取景由它自己決定，模型較小。
  • PixelOver 模型較小：樣本甲 量到 134×162，補透明邊成 162×162 後仍比另外兩邊小——影響邊界比例絕對值，不影響抖動比例（那是相對於不透明像素算的）。
  • 樣本乙、樣本丙 在 PixelOver 內把節點放大到 140% 才對齊到 162 高（樣本乙 139×162、樣本丙 148×162）；樣本甲 是預設比例、未放大，這是三台間的已知差異。
  • 抖動強度尺度三邊不同：PixelOver 是百分比（設 50%）、PixelBake 是 0～1（設 0.6）、Pixelate 沒有獨立參數，不能直接換算，只能比結果。
  • 抖動樣式不同：PixelBake 用 Bayer 4×4；PixelOver 用內建預設圖案；Pixelate 沒有公開樣式選項。
  • 打光不同：PixelBake 用三點打光＋環境光，另外兩個用各自預設——色調差異主要來自這裡，不是像素演算法。
